Что именно мы загружаем: файл, таблицу или поездки?

  1. pd.read_csv(...) читает текст с разделителями и превращает его в DataFrame. Названия из первой строки становятся колонками; остальные строки становятся записями. raw_trips = ... сохраняет эту таблицу в памяти.
  2. head() показывает первые пять строк, а не все данные. Это окно для знакомства: проверить названия, единицы и вид значений. tail() смотрит конец, где в этом примере и спрятаны повторные строки.
  3. shape возвращает пару (строки, колонки). Это свойство, поэтому после shape нет круглых скобок. У head() скобки есть, потому что это действие, метод.
  4. У первой строки trip_id=1001 статус cancelled. Её дистанция, длительность и оплата неизвестны/не применимы. У второй, trip_id=1002, поездка завершена: 3 км, 12,7 минуты, 1100 ₸.
  5. Число слева от строки в обычном выводе pandas является индексом. Оно не считается девятым столбцом. Не путайте индекс 0 с trip_id=1001.

Как удалить технический повтор, но не потерять настоящую заявку?

  1. info() отвечает «какие типы и сколько заполнено?». describe() отвечает «как распределены числовые значения?». Например, count в describe может быть меньше числа строк из-за пропусков. Это не противоречие.
  2. duplicated() сравнивает все поля и отмечает лишний экземпляр повторной строки. .sum() считает True как 1. Здесь результат 2: два лишних экземпляра, а не четыре разных заявки.
  3. duplicated(keep=False) отмечает все экземпляры повторов. Поэтому на экране увидите четыре строки: по две копии ID 1009 и 1044. Показать обе копии полезно до удаления.
  4. drop_duplicates() оставляет по одной копии каждой полностью одинаковой строки. .copy() создаёт отдельную рабочую таблицу. Сырой raw_trips сохраняем, чтобы можно было вернуться и объяснить изменение.
  5. trips["trip_id"].is_unique проверяет ID. Если после удаления полных повторов одинаковые ID остались, значит строки отличаются. Выбрать одну без разбора нельзя: возможно, это обновления статуса или конфликт.
  6. isna() выдаёт маску пропусков. sum() считает их количество, mean() * 100 долю среди всех строк. После очистки знаменатель равен 168, не 170.
Что должно получиться
170 строк − 2 полных повтора = 168 уникальных заявок. Пропусков duration_min: 31 = 29 отмен + 2 завершённые поездки (ID 1010 и 1077). Из 139 завершённых известна длительность у 137.

Как это объяснить человеку

Удалены две повторные записи, а не две поездки. Пропуски длительности имеют две причины: поездка не состоялась либо измерение потерялось. Для отчёта о длительности нужны только известные измерения завершённых поездок.

Частая ошибка

dropna() без выбора колонок удалит каждую строку с любым пропуском. Так исчезнут все отмены и часть полезных поездок, а доля отмен станет бессмысленной. Нельзя «очистить» таблицу до удобного результата.

  1. trips["status"] выбирает одну Series. trips[["trip_id", "status"]] получает список названий и возвращает таблицу. Двойные скобки не украшение: внешние выбирают, внутренние создают список.
  2. trips.iloc[0:3, 0:5]: до запятой стоят строки, после запятой колонки. Позиции считаются с нуля; конец 3 не включается, поэтому берём позиции 0, 1, 2.
  3. set_index("trip_id", verify_integrity=True) создаёт новую таблицу, где ID служит адресом строки. Присваиваем её by_id. Проверка verify_integrity не разрешит повторные адреса.
  4. by_id.loc[1002] ищет метку 1002. by_id.iloc[1] выбирает вторую по порядку строку. В этом конкретном порядке они показывают одну заявку, но после сортировки это совпадение может исчезнуть.
  5. При выборе нескольких ID используем список: by_id.loc[[1002, 1003], ["status", "fare_kzt"]]. Первая часть выбирает строки, вторая ограничивает поля.

Чтобы перевести минуты в часы, не нужен цикл по строкам: pandas применит деление ко всему столбцу. Для учебных признаков создадим копию, исходный trips оставим понятным.

PYTHON / ЗАПУСКАЙТЕ ПО ПОРЯДКУ В NOTEBOOK
analysis = completed.copy()

analysis["fare_per_km"] = analysis["fare_kzt"] / analysis["distance_km"]

Как читать fare_per_km: это записанная сумма оплаты, делённая на дистанцию конкретной поездки. Это не доказанная ставка тарифа: в сумме может быть фиксированная часть. Короткая поездка поэтому может быть дороже «за километр».

Пропуск длительности при делении остаётся пропуском. Мы не восстанавливаем неизвестное измерение арифметикой.

Что значит «деление применяется ко всему столбцу»?

  1. analysis = completed.copy() создаёт место для учебных признаков. Здесь нет отмен, поэтому расчёты расстояния и оплаты относятся к состоявшимся поездкам.
  2. analysis["duration_min"] / 60 делит каждую известную длительность на 60. Результат это Series с тем же индексом. Присваиваем её новой колонке duration_hours.

Векторная операция делает одинаковый расчёт для всех строк. Мы меняем единицы или создаём отношение, но не получаем новую информацию о потерянных измерениях.

Что внутри groupby, size, count и agg?

  1. groupby("channel", dropna=False) мысленно складывает заявки в четыре стопки: app, phone, web и неизвестный канал. Таблица ещё не стала сводкой, пока вы не указали, что считать.
  2. .size() считает строки каждой стопки. ["duration_min"].count() считает только непустые длительности. Поэтому эти числа могут различаться даже для одной группы.
  3. В agg(requests=("trip_id", "size")) слева requests это имя новой колонки; внутри пары trip_id это исходная колонка, size операция. Другие пары добавляют новые показатели рядом.

  5. Для денежного отчёта начинаем с completed. sum складывает оплаты, median описывает типичную оплату, size считает поездки. Одна колонка не заменяет остальные.

Почему дата выглядит правильно, но остаётся строкой?

9. merge: добавляем названия зон по ключу

У нас отношение многие к одному: много заявок могут приходить из одной зоны.

  • on="zone_id" — ищем совпадение по коду зоны.
  • how="left" — сохраняем каждую заявку из левой таблицы.
  • validate="many_to_one" — проверяем, что справа код не повторяется.
  • indicator=True — добавляем служебный столбец с результатом поиска пары.

Это тот же смысл, который позже появится в SQL JOIN. Сейчас важнее понимать строки, чем запоминать все параметры.

Как pandas находит название для каждой заявки?

  1. Левая таблица trips содержит заявки. Правая zones содержит справочник. Для каждой строки слева pandas берёт zone_id и ищет точно такой же ключ справа. Порядок строк не имеет значения.

  3. on="zone_id" указывает ключ. how="left" требует сохранить все строки левой таблицы, даже если пары справа нет.
  4. validate="many_to_one" разрешает много заявок на одну зону, но запрещает несколько записей одного ключа справа. Это проверка отношения, не способ очистить справочник.

Измените способ объединения

Результаты заранее вычислены для того же снимка. Выбор показывает последствие, а не запускает Python.

Ни LEFT, ни INNER не «лучше всегда». Здесь задача сохранить все заявки, поэтому выбираем LEFT и явно помечаем неизвестную зону.

РАЗБИРАЕМ МЕДЛЕННО / КАК И ПОЧЕМУ

Какие три проверки делают объединение безопаснее?

  1. assert len(joined) == len(trips) сравнивает количество строк до и после. Если стало меньше, потеряли заявки; если больше, могли размножить их. Для этого LEFT many-to-one ожидается точное равенство.
  2. assert joined["trip_id"].is_unique проверяет, что каждую заявку по-прежнему видим один раз. Одно количество строк не гарантирует, что не исчезла одна строка и не продублировалась другая.
  3. np.isclose(sum_after, sum_before) сравнивает суммы с допуском к погрешности десятичных вычислений. Это не произвольное разрешение терять деньги: бизнес-правила денежных расчётов в реальной системе требуют своих правил точности.
  4. INNER оставляет только найденные пары. В нашем наборе он удаляет заявку 1093. Поэтому строк становится 167, а оплата уменьшается на 2700 ₸. Для задачи полного отчёта это потеря.
  5. В демонстрации bad_zones добавляется вторая запись Z01. Теперь к заявке Z01 подходят две правые строки. validate вызывает MergeError раньше, чем завышенная сумма попадёт в отчёт.
  6. Ошибка перехвачена try/except намеренно только в учебном примере. В рабочем анализе нельзя молча проигнорировать проблему: нужно исправить справочник или уточнить правило объединения.

Как это объяснить человеку

Проверки не доказывают абсолютную правильность исходных данных. Они доказывают конкретные свойства преобразования: не изменили число заявок, не размножили ID, сохранили сумму. Полезно вслух назвать, что именно проверено.

Частая ошибка

Убрать validate, чтобы исчез MergeError, всё равно что выключить сигнализацию вместо устранения причины. Ошибка проверки это информация о данных, а не помеха, которую надо спрятать.

12. Сохраняем CSV и JSON и читаем обратно

Отчёт полезен, когда его может открыть другой человек. Сохраним одинаковую небольшую таблицу в двух форматах.

  • CSV удобен для таблиц и Excel. index=False не добавляет служебный индекс отдельным столбцом.
  • JSON orient="records" — список объектов, по объекту на строку отчёта.
  • force_ascii=False оставляет кириллицу читаемой в текстовом JSON.

Исходные файлы не перезаписываем: всё отправляется в отдельную папку output/ текущего запуска.
